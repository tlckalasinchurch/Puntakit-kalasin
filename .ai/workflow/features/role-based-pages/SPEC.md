## 1. เจตนาและเหตุผล (Intent & Rationale)

เอกสารข้อเสนอผลิตภัณฑ์ `Puntakit-Role-Based-Pages.md` ต้องการจัดระเบียบหน้าจอให้ตรงกับความรับผิดชอบของผู้ใช้ 6 กลุ่ม แต่ระบบปัจจุบันมีโครงสร้างสิทธิ์ผ่าน 7 บทบาทจริงใน `shared/schema.ts` และการคำนวณ Data Scope ฝั่ง Server 

เป้าหมายของฟีเจอร์นี้คือ:
1. ปรับปรุงทางลัดหน้าแรก (`HomeMyWork` / Quick Action Tiles) ให้แต่ละบทบาทเห็นงานที่ตนเองต้องทำบ่อยที่สุดอย่างชัดเจน (Mobile-first, Quick actions first)
2. แก้ไขปัญหาความไม่สอดคล้องของ Data Scope สำหรับหัวหน้าบอดี้ใน `server/lib/careScope.ts` ให้รวมกลุ่มลูก (Descendant Groups) ภายใต้บอดี้ที่ตนนำ เพื่อให้เข้าถึงข้อมูลใน `/care` ได้อย่างถูกต้องและไม่เจอหน้าว่างที่ทำให้สับสน
3. คงโครงสร้างเดิม ไม่สร้าง Role ใหม่ และไม่รื้อระบบเมนูพร้อมกันทั้งหมดในรอบนี้

## 2. เป้าหมาย / ไม่ใช่เป้าหมาย / Anti-goals

### เป้าหมาย (Goals)
- **G1:** กำหนด Role Mapping ระหว่างกลุ่มผู้ใช้ในข้อเสนอกับ Role จริงในระบบอย่างรัดกุม โดยไม่เพิ่ม Role ใหม่
- **G2:** หน้าแรก (`HomeMyWork.tsx` + `homeTiles.ts`) มีชุดทางลัดเฉพาะสำหรับแต่ละบทบาทตามสิทธิ์จริง
- **G3:** ปรับปรุง Data Scope ใน `careScope.ts` ให้รองรับบอดี้และกลุ่มลูกอย่างถูกต้อง ปลอดภัย และไม่รั่วไหลไปยังกลุ่มอื่น
- **G4:** รักษา Design System V2: ใช้ Prompt, Teal `--color-primary: #0c7c82`, Target ≥ 44px, Contrast ≥ 4.5:1

### ไม่ใช่เป้าหมาย (Non-goals)
- ไม่เพิ่ม Role ใหม่ (`coordinator`, `pastor`, `team_leader`) หรือสร้างตาราง Schema/Migration ใหม่
- ไม่สร้างหน้าจอใหม่สำหรับโมดูลที่ไม่มีจริงในระบบ (Audit Logs UI, System Settings, Security, Handover, Team Performance)
- ไม่รื้อหรือเปลี่ยน Sidebar Navigation และ Routing ทั้งหมดพร้อมกัน (จำกัดเฉพาะ Vertical Slice ของ Home และ Care Scope)
- ไม่แตะไฟล์ล็อกอิน `PinSignInPage.tsx`, บล็อก `.pin-login` ใน `index.css`, หรือ `stash@{0}`

### Anti-goals (ถือว่าล้มเหลวแม้ระบบจะทำงานได้)
- การขยายสิทธิ์จนผู้ใช้เห็นข้อมูลนอกขอบเขตความรับผิดชอบ (Data Scope Leak)
- การให้สิทธิ์ `admin` แก่ผู้ใช้โดยพลการเพื่อแก้ปัญหาการเข้าถึงหน้าจอ
- การเปลี่ยนฟอนต์เป็น Sarabun หรือเพิ่มโทเค็นสี `#35B4B0` นอกเหนือ Design System เดิม
- การใช้ Mock Data เพื่อทำให้หน้าจอดูเหมือนมีข้อมูลสมบูรณ์

## 5. การออกแบบพื้นผิวและพฤติกรรม (Surface Design)

### 5.1 หน้าแรกและไทล์ทางลัด (`HomeMyWork.tsx` & `homeTiles.ts`)
- **โครงสร้างการแสดงผล:**
  1. ส่วนหัว "ทำต่อได้เลย" + ปุ่มเปิด/ปิด "ดูทั้งหมด" (`aria-expanded`)
  2. ไทล์หลักตามบทบาท (วงกลมไอคอน ≥ 64px, พื้นที่กด ≥ 44px, สูง ≥ 120px)
  3. รายการลิงก์ทางลัดเพิ่มเติมใต้ "ดูทั้งหมด" (เมื่อเปิด)
  4. ส่วนเนื้อหาขึ้นกับสถิติ (สถิติของฉัน / ภาพพันธกิจล่าสุด) ซึ่งหากโหลดไม่สำเร็จ จะแสดง `ErrorState` ใต้ไทล์หลักเสมอ (ผู้ใช้ยังกดไทล์ได้)
- **ชุดไทล์หลักตามบทบาท:**
  - `group_leader` (บอดี้/แคร์): `care` (เช็คชื่อกลุ่มดูแล), `photo` (อัปเดตภาพพันธกิจ), `membership` (สถานะสมาชิก) · ลิงก์รอง: `/follow-up`, `/groups`, `/members`
  - `ministry_leader`: `care` (เช็คชื่อ), `photo` (ภาพพันธกิจ), `followUp` (การติดตาม) · ลิงก์รอง: `/ministries`, `/feed`, `/events`
  - `staff` / `admin` / `super_admin`: `care`, `photo`, `membership`, `followUp` · ลิงก์รอง: ครบตามสิทธิ์
  - `viewer`: `followUp` (การติดตามของฉัน) · ลิงก์รอง: รายการที่เปิดได้

### 5.2 การปรับปรุง Care Data Scope (`server/lib/careScope.ts`)
- **ปัญหาเดิม:** `getLedGroupIds(userId)` ใน `careScope.ts` ดึงเฉพาะกลุ่มที่ `leaderId === userId` เมื่อหัวหน้าบอดี้ไม่ได้ลงชื่อเป็นผู้นำแคร์ลูกโดยตรง กลุ่มแคร์ลูกจึงไม่ถูกนับ ทำให้หน้า `/care` ว่างเปล่า
- **พฤติกรรมใหม่:**
  1. ดึงกลุ่มที่ผู้นำนำโดยตรง (`led`)
  2. ขยายกลุ่มด้วย `withDescendantGroups(led)` (cycle-safe hierarchy traversal)
  3. สมาชิกในกลุ่มลูกเหล่านั้นจะถือว่าอยู่ใน Scope ของหัวหน้าบอดี้สำหรับการอ่านและการเช็คชื่อ
  4. การปฏิเสธสิทธิ์ (403): หากพยายามเข้าถึงกลุ่มอื่นที่ไม่ใช่ลูกของบอดี้ตนเอง ต้องโยน `ForbiddenError` อย่างเข้มงวด (เช่น `GET /api/care/groups/:id/roster`)
  5. **ขอบเขตจริงที่เจ้าของอนุมัติ (2026-10-17):** ขยายเฉพาะฝั่งอ่าน (`getViewableGroupIds`/`viewsGroup`/`getViewableMemberIds` ใน `careScope.ts`: `/api/care/groups`, roster, `GET /api/members`, `/:id`, export) ฝั่งเขียนคงเป็นผู้นำโดยตรง (`getLedGroupIds`, `assertGroupWriteAccess`, `PUT /api/members/:id`) หัวหน้าบอดี้ดู roster ได้แต่บันทึกเช็คชื่อแทนแคร์ลูกไม่ได้ (เหมือน `canDecide`)
  6. `GET /api/members/:id` ของสมาชิกนอก scope ตอบ **404** (ไม่ใช่ 403) ตามพฤติกรรมเดิมเพื่อกัน ID enumeration

## 6. ข้อกำหนดสถานะหน้าจอ (State Specifications)

- **Loading State:** แสดง Skeleton แทนที่ข้อมูลเสมอ ไม่ใช้ข้อความจุดไข่ปลา `...`
- **Empty State:** ข้อความสื่อความหมายชัดเจนตามจริง หากไม่มีสมาชิกในกลุ่มแจ้งให้เพิ่มสมาชิก หากมีคำค้นหาแสดง "ไม่พบข้อมูลที่ตรงกับคำค้น"
- **Error State:** แสดง `ErrorState` พร้อมปุ่ม "ลองอีกครั้ง" สำหรับข้อผิดพลาดเครือข่าย/เซิร์ฟเวอร์ และแสดงคำอธิบายสิทธิ์ชัดเจนเมื่อติด 403
- **Success State:** แสดง Toast การทำงานชัดเจน (เช่น ระบุสถานะฉบับร่าง)

## 7. ข้อกำหนดด้านการเข้าถึงและดีไซน์ (A11y & Design)

- **Touch Targets:** ทุกปุ่ม ไทล์ และแถวรายการต้องมีขนาดไม่น้อยกว่า 44×44px
- **Contrast Ratio:** ข้อความปกติ ≥ 4.5:1, ไอคอนและชิ้นส่วนกราฟิก ≥ 3:1
- **Viewport Support:** รองรับขนาดหน้าจอ 320px, 390px, 768px และ 1280px โดยไม่มี Horizontal Overflow
- **Dark Mode:** พื้นหลังโทนเข้มอ่านสบายตา เส้น hairline คมชัด ไม่กลืนกับพื้นหลัง
- **Reduced Motion:** เคารพการตั้งค่า `prefers-reduced-motion` โดยปิด transition/animation
