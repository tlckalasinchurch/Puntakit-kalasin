# ADR 002: โครงสร้างองค์กรสามระดับและคำศัพท์ (body → ระดับกลาง "แคร์" → `care` "พันธกิจ")

- **Status:** proposed
- **Date:** 2026-10-09
- **Deciders:** เจ้าของโปรเจกต์ (session 2026-10-09 — **ยังไม่ผ่านการตรวจรับ ยังไม่ `accepted`**)
- **Supersedes:** —
- **Revision note:** ร่างแรกวันเดียวกันเสนอ `body → care → home` (ให้ `care` เป็นระดับกลาง) หลักฐานในโค้ดและชุดข้อมูลที่พบภายหลังชี้ว่าแถว `care` เดิมน่าจะเป็นหน่วยล่างสุด จึงเปลี่ยนทิศทางตาม Q23 ด้านล่าง ADR ยัง `proposed` จึงแก้เนื้อหาได้ตามกฎใน `docs/adr/README.md`

> **ADR นี้เป็นแหล่งอ้างอิงหลักของ (1) ตารางศัพท์ระดับองค์กร และ (2) ขั้นตอนตรวจ Production (Q24)** เอกสารอื่นให้ชี้มาที่นี่ ไม่ทำสำเนา

## ตารางศัพท์ (แหล่งเดียว)

| ระดับ | ป้ายที่ผู้ใช้เห็น | ชื่อเชิงเทคนิค | สถานะ |
|---|---|---|---|
| ศบ. (หัวหน้าทีม/ศิษยาภิบาล) | "ศบ.อาจารย์ / หัวหน้าทีม" | ไม่ใช่แถวใน `groups` — เป็นค่าคงที่ `HEAD_ROLE` (`shared/orgView.ts`) | เดิม |
| บอดี้ | บอดี้ | `body` | เดิม |
| **ระดับกลาง "แคร์"** | แคร์ (ป้ายใหม่ — **ยังไม่ยืนยัน**) | **ยังไม่กำหนด** (ไม่มีในโค้ด) | **Proposed** (Q23) |
| หน่วยล่างสุด "พันธกิจบ้าน" | **พันธกิจ** (มติเดิม **ไม่เปลี่ยน**) | `care` | เดิม ตามหลักฐานในโค้ด — **ยังไม่ยืนยันกับ production** |

ข้อควรระวัง: ในคำศัพท์เดิม "ผู้นำแคร์" คือผู้นำของ `care` (`ARCHITECTURE.md` §10) ส่วน "หัวหน้าแคร์" ในข้อกำหนดใหม่คือผู้นำของ **ระดับกลาง** ทั้งสองคำห้ามใช้ปะปนในเอกสารและโค้ดจนกว่าจะยืนยันศัพท์

## Context

เจ้าของโปรเจกต์อธิบายโครงสร้างจริงเป็นบอดี้ (ราว 6) → แคร์ (ราว 20) → พันธกิจบ้าน (ราว 52 ทำได้จริงราว 49) **ตัวเลขทั้งหมดยังไม่ผ่านการตรวจสอบ** (`NOT VERIFIED`) เพราะไฟล์ Excel ต้นฉบับและรายงานตัวอย่างไม่อยู่ในสภาพแวดล้อมที่ตรวจ และขัดกับเอกสารเดิม (~23 กลุ่ม; audit นับ 72 sheet สมาชิก — `PUNTAKIT_MISSION_SOURCE_AUDIT.md`)

**โค้ดวันนี้รองรับสองระดับ:** `GROUP_ORG_LEVELS = ["body","care"]` (`shared/schema.ts`), `assertOrgHierarchy` (`server/routes/groups.ts`: บอดี้ไม่มีกลุ่มแม่ และแม่ของ `care` ต้องเป็น `body`), `server/routes/org.ts` (ผัง ศบ. → body → care → member)

**หลักฐานว่าแถว `care` เดิมน่าจะเป็นหน่วยล่างสุด (ไม่ใช่ระดับกลาง):**
- ตัวโหลดข้อมูลองค์กร `server/lib/orgDataset.ts` (ผ่าน `/api/org-data/*`, admin) สร้างแถว `care` **หนึ่งแถวต่อหนึ่งชีต** พร้อม `village`, `tambon`, `amphoe`, `province`, `care_code`, `care_leader_raw`, `coordinator_raw`
- คอมเมนต์ `shared/schema.ts:219`: "care (พันธกิจ, led by หนค.)"
- UI เรียก `care` ว่า "พันธกิจ" ตามมติเดิม

**ข้อจำกัดของหลักฐานนี้:** มาจากโค้ดและโครงสร้างชุดข้อมูล ไม่ใช่ข้อมูลจริงใน production ซึ่ง **ยังไม่ได้ตรวจ** (Q24) และไม่รู้ว่า `/api/org-data/apply` เคยรันบน production หรือไม่ นอกจากนี้ตัวย่อ "หนค."/"หนบ." ไม่มีคำเต็มในโค้ด และไม่ชัดว่า "หัวหน้าแคร์" ของระดับกลางเป็นคนละคนกับ "หนค." ของแต่ละ `care` หรือไม่

**ความเสี่ยงโมเดลซ้อนกัน:** แผน `MISSION_DOMAIN_PLAN` §2/§18 เสนอคอลัมน์ `groupKind` (ยังไม่มีในโค้ด) สำหรับกลุ่มพันธกิจบ้านจาก Excel ชุดเดียวกัน ขณะที่ org-data สร้างแถว `care` จากชุดเดียวกันแล้ว ถ้า production เคยใช้ org-data การเพิ่ม `groupKind` ภายหลังเสี่ยงสร้างกลุ่มซ้ำ

**ข้อมูลเพิ่มเติมของ `careGroupId`:** ไม่ใช่คอลัมน์ในฐานข้อมูล เป็นฟิลด์ของ API ความหมายถูกกำหนดโดย `requireCareGroup` (`server/lib/careMembership.ts`): ต้องเป็นกลุ่ม `org_level='care'` และสมาชิกมีสังกัด `care` ที่ active ได้หนึ่งกลุ่ม พบใน 4 ไฟล์ที่ไม่ใช่เทสต์ (`members.ts`, `careMembership.ts`, `validation.ts`, `Members.tsx`) และ 1 ไฟล์เทสต์

## Decisions

### ตัดสินแล้ว (เจ้าของยืนยันใน session; ADR ยังไม่ `accepted`)

1. โครงสร้างมี **สามระดับ**: บอดี้ → ระดับกลาง → หน่วยล่างสุด
2. **ห้ามเปลี่ยนความหมายของ `careGroupId` เดิมโดยอัตโนมัติ** — ต้องตรวจทุกจุดใช้งานและมีแผนเปลี่ยนผ่านข้อมูลก่อน
3. **ห้ามย้ายหรือสร้างข้อมูลกลุ่มใหม่ เพื่อทำให้ตัวเลขตรงสมมติฐาน** — แถวระดับกลางต้องมาจากแหล่งที่ตรวจสอบแล้วเท่านั้น
4. **ห้ามเปลี่ยนป้าย UI ที่มีมติเดิมโดยพลการ** (รวม "พันธกิจ" บน `care`)
5. ไม่แก้โค้ด schema หรือ migration ในงานเอกสาร

### เสนอจากหลักฐานปัจจุบัน (Proposed — **เงื่อนไข Q24 ยังไม่ผ่าน**)

**Q23:** `care` (UI "พันธกิจ") คือหน่วยล่างสุดที่มีอยู่แล้ว; "แคร์" เป็น **ระดับกลางใหม่** ระหว่าง `body` กับ `care` ที่รวมหลายพันธกิจบ้านเข้าด้วยกัน ผลที่ตามมาถ้าถูกต้อง:
- ไม่ต้องย้ายข้อมูล `care` เดิมไปชื่ออื่น ไม่ต้องเปลี่ยนป้าย "พันธกิจ" และ `careGroupId`/`careMembership` ยังหมายถึง `care` ล่างสุดตามเดิม
- ต้องเพิ่มระดับกลาง (กระทบ `GROUP_ORG_LEVELS`, `assertOrgHierarchy`, `org.ts`, UI ผังองค์กร และต้องจัด `care` เดิมเข้าใต้แถวระดับกลางจากข้อมูลที่ตรวจสอบแล้ว)
- สมาชิกสังกัดเฉพาะ `care` ล่างสุด ส่วนระดับกลางและบอดี้ **อนุมานจาก `parentGroupId`** (ข้อเสนอ ยังไม่ตัดสิน)

### กฎตัดสินล่วงหน้าเมื่อได้ผล Q24 (ไม่ใช่ผลที่ตรวจแล้ว)

| ผล `data.totals.careGroups` / ประวัติ org-data | ผลต่อ ADR นี้ |
|---|---|
| ใกล้ 52 และมีข้อมูลหมู่บ้าน/ผู้ประสานงาน | สนับสนุน Q23 |
| ใกล้ 20 | **ไม่สนับสนุน Q23** — ต้องกลับมาตัดสินใจใหม่ (ทางเลือกร่างแรก: `care` เป็นระดับกลาง เพิ่มระดับล่างใหม่) |
| 0 หรือไม่เคยรัน org-data | ไม่มีข้อมูลต้องย้าย แต่ยังไม่มีหลักฐานเรื่องโครงสร้างจริง — ตรวจกับไฟล์ต้นฉบับ |
| ค่าอื่น | **สรุปไม่ได้** — ห้ามเดา |

## Production Verification (Q24) — **NOT VERIFIED**

ผมไม่มีสิทธิ์เข้า production และไม่ได้เรียกระบบจริง สิ่งที่ผู้ดูแลระบบทำได้ (read-only):

1. **จำนวนบอดี้/care/สมาชิก:** ล็อกอินด้วยบัญชีที่มีสิทธิ์ (`PRIVILEGED_ROLES`) แล้ว `GET /api/org/overview` บนระบบจริง (host ตามที่แผน `MISSION_DOMAIN_PLAN` §Open blocker ใช้กับ pre-check) ฟังก์ชัน `loadOrgOverview` (`server/routes/org.ts`) เป็น SELECT อย่างเดียว คืน `data.totals = { bodies, careGroups, members }` และ `data.unassignedCareGroups` **ให้คัดลอกเฉพาะ 4 ค่านี้ ไม่ส่งชื่อคนหรือชื่อกลุ่ม** (response มีชื่อ)
2. **เคยรัน `org-data/apply` หรือไม่:** route นี้บันทึก `audit_logs` ด้วย `action` = `ORG_DATASET_LOADED` / `ORG_DATASET_ROLLED_BACK` (ค่า details เป็นจำนวน ไม่มีข้อมูลส่วนบุคคล) **ไม่มี API ที่อ่าน `audit_logs`** จึงต้องมีผู้ถือสิทธิ์อ่านฐานข้อมูล: `SELECT action, created_at FROM audit_logs WHERE action IN ('ORG_DATASET_LOADED','ORG_DATASET_ROLLED_BACK') ORDER BY created_at;` ถ้าไม่มีสิทธิ์ = ยังเป็น `NOT VERIFIED`

**ข้อจำกัดสำคัญ:** ผลข้างบนยืนยันได้เฉพาะจำนวน **บอดี้** และ **`care`** (ระดับกลางไม่มีในฐานข้อมูล) จึง **ตัวเลข "20 แคร์" ตรวจจากฐานข้อมูลไม่ได้เลย** ต้องตรวจจากรายงานตัวอย่าง/ไฟล์ต้นฉบับ ซึ่งยังไม่มี

## Consequences

**ดี:** ตรงกับสายบังคับบัญชาจริง ขอบเขตสิทธิ์ (ADR 003) และรายงาน (ADR 004) ใช้ลำดับชั้นเดียวกัน และทิศทางนี้ลดการเปลี่ยนแปลงต่อโค้ด/ข้อมูลเดิมเมื่อเทียบกับร่างแรก

**แย่:**
- ถ้า Q24 ไม่สนับสนุน Q23 ต้องกลับมาตัดสินใหม่ และงานที่เขียนบนทิศทางนี้ (ADR 003/004, PRD) ต้องปรับตาม
- แหล่งข้อมูลที่บอกว่า `care` ใดอยู่ใต้ "แคร์" ใดยังไม่มี (NOT VERIFIED) จึงสร้างแถวระดับกลางและจัดสังกัดไม่ได้
- ความหมายของ "หนค." เทียบ "หัวหน้าแคร์" ยังไม่ยืนยัน อาจต้องแยกสองตำแหน่งในข้อมูลและ UI
- ความเสี่ยงโมเดลซ้อนระหว่าง org-data และ `groupKind` ยังเปิดอยู่

**เป็นกลาง:** `shared/orgView.ts` ยังแปลกลับป้ายเดิม `รหัสแคร์` และ `หนค. (ต้นฉบับ)` จากข้อมูลนำเข้า — ไม่เปลี่ยนในงานนี้

## Open decisions (ยังไม่ยืนยัน)

| # | เรื่อง |
|---|---|
| O1 | ชื่อเชิงเทคนิคของระดับกลาง และการยืนยันป้าย "แคร์" |
| O2 | วิธีให้สมาชิกสัมพันธ์กับระดับกลาง (ข้อเสนอ: อนุมานจาก `parentGroupId`) |
| O3 | `groupKind` กับ `orgLevel` และความเสี่ยงสร้างกลุ่มซ้ำกับ org-data |
| O4 | ตัวเลข 6/20/52/49 (`NOT VERIFIED`) และผล Q24 |
| O5 | ความหมายตัวย่อ "หนค."/"หนบ." และความสัมพันธ์กับ "หัวหน้าแคร์" |
| O6 | แหล่งข้อมูลที่ยืนยันว่า `care` ใดอยู่ใต้แคร์ใด |

## Alternatives considered

| ทางเลือก | ทำไมไม่เลือก (ณ ตอนนี้) |
|---|---|
| ร่างแรก: `body → care → home` (`care` เป็นระดับกลาง) | ต้องย้ายแถว `care` เดิมไปเป็นระดับล่างและเปลี่ยนความหมายหลายจุด (`careGroupId`, `careMembership`, ป้าย) — **กลับมาพิจารณาหาก Q24 ชี้ว่า `care` ≈ 20** |
| คงสองระดับ ใช้ "แคร์" เป็นแค่ป้ายผู้นำ | รายงานและสิทธิ์รายแคร์ต้องมีแคร์เป็นหน่วยในโครงสร้าง |
| ใช้ `area` (ภูมิศาสตร์) แทนระดับองค์กร | ภูมิศาสตร์ ≠ สายบังคับบัญชา (แผน §11 แยกไว้แล้ว) |
| เปลี่ยนป้าย UI ทันทีเมื่อเพิ่มระดับ | ขัดกับมติเดิม |
