# ADR 003: ขอบเขตสิทธิ์ตามสายบังคับบัญชา, บทบาท `team_lead`, และข้อมูลส่วนบุคคลของสมาชิก

- **Status:** proposed
- **Date:** 2026-10-09
- **Deciders:** เจ้าของโปรเจกต์ (session 2026-10-09 — **ยังไม่ผ่านการตรวจรับ ยังไม่ `accepted`**)
- **Supersedes:** — (ปรับแผนเดิม `MISSION_DOMAIN_PLAN` §16 บางแถว ดู Context)

> ศัพท์ระดับองค์กร (บอดี้ / "แคร์" ระดับกลาง / `care` = "พันธกิจ") ดู [ADR 002](./adr-002.md) — ที่นี่ไม่ทำสำเนา ชื่อบทบาทในตารางด้านล่างเป็นตำแหน่งตามผู้นำจริง ไม่ใช่ค่าใน `USER_ROLES` ยกเว้น `team_lead` (ข้อเสนอ)

**สถานะการลงมือ: ยังไม่ได้ implement สิ่งใดในเอกสารนี้ ไม่มีบทบาท `team_lead` ในโค้ด ไม่ได้แก้ระบบ Authorization และ _ยังไม่มี security tests_ ของข้อกำหนดนี้**

## Context

ระบบสิทธิ์มีระบบเดียว (`USER_ROLES` + ชุดสิทธิ์ใน `shared/roles.ts`) และ `group_leader` เห็นเฉพาะกลุ่มที่ตนนำ (`getLedGroupIds`, `resolveGroupScope` ใน `server/lib/groupAccess.ts`) **ไม่มีขอบเขตที่ครอบคลุมกลุ่มลูก** ผู้นำคือผู้ที่ระบุที่ `groups.leaderId`, `groups.coLeaderId` หรือสมาชิกที่มีบทบาท `leader`/`assistant_leader`

ข้อเท็จจริงที่กระทบการตัดสินใจ:

- `admin`/`super_admin` ลบสมาชิก/กลุ่ม จัดการกิจกรรม/ประกาศ/ฝ่ายงาน แก้ข้อมูลคริสตจักร นำเข้า Excel จัดการข้อมูลซ้ำ และทำ org-data apply/rollback ได้ (`requireAdmin`/`ADMIN_ROLES`) — มากกว่าหน้าที่ของหัวหน้าทีม
- `staff` ไม่มีสิทธิ์ทำลายข้อมูล แต่เห็นเบอร์/อีเมลจริงของสมาชิกทุกคนและส่งออก CSV รายคนได้ (`MEMBER_CONTACT_ROLES`, `PRIVILEGED_ROLES`) จึงขัดหลักเปิดเผยน้อยที่สุด
- `/api/reports` ทั้งหมดรวมการส่งออก CSV จำกัดที่ `PRIVILEGED_ROLES` (`super_admin`, `admin`, `staff`, `ministry_leader`) `viewer` เข้าไม่ได้ **ไม่มีบทบาทเดิมที่ตรงกับ "อ่านและส่งออกเฉพาะตัวเลขรวม"**
- `ministry_leader` คือหัวหน้าฝ่ายงาน (จัดการกลุ่มได้ทุกกลุ่ม) ไม่ใช่หัวหน้าบอดี้/แคร์
- `ARCHITECTURE.md` §10 Glossary นิยาม "ผู้นำแคร์ = บทบาท `group_leader`" และ "ศิษยาภิบาล = ไม่มีในโค้ด" — ADR นี้เปลี่ยนวิธีคิดเป็น "ผู้นำ = ผู้ที่นำกลุ่มระดับนั้นจริง" **`ARCHITECTURE.md` §10 ยังไม่ถูกแก้** (รายการแก้อยู่ในรายงานปิดงาน 2026-10-09)
- แผนเดิม §16 ให้ `GROUP_MANAGE_ANY_ROLES` (ระดับ admin) รับรองรายงาน และผู้ประสานงานในแผนเดิมไม่ใช่ผู้ใช้ — การเชิญเข้า Clerk ถูกจัดเป็น out-of-scope ต้องตัดสินใหม่เมื่อผู้นำต้องส่งรายงานเอง
- ไม่มี UI จัดการบทบาท (`PRD.md` T3) การมอบบทบาทวันนี้ทำผ่านฐานข้อมูล/bootstrap เท่านั้น

## Decisions

### ตัดสินแล้ว (เจ้าของยืนยัน; ADR ยังไม่ `accepted`)

1. **ขอบเขตสิทธิ์ = ผู้นำจริงของกลุ่ม + ลำดับชั้น `parentGroupId`** ไม่เพิ่มบทบาทตามระดับองค์กรใน `USER_ROLES` (ไม่สร้างระบบสิทธิ์ที่สอง)
2. สิทธิ์แยก **read, create, update, approve, export, delete** ออกจากกัน
3. **หัวหน้าทีมไม่ใช้ `admin` อัตโนมัติ** เพราะสิทธิ์ลบเกินหน้าที่
4. **delete เป็นของ `admin`/`super_admin` เท่านั้น** ไม่มีตำแหน่งตามสายบังคับบัญชาใดลบข้อมูลได้
5. **ข้อกำหนดบทบาท `team_lead`** (บันทึกเป็นข้อเสนอที่รอ implementation ยังไม่สร้างบทบาท):
   - มองเห็นภาพรวมองค์กรและรายงานของทุกบอดี้
   - มอบเป้าหมายและติดตามความคืบหน้าของรายงาน
   - **ไม่มีสิทธิ์ลบสมาชิกหรือลบกลุ่ม** (ไม่ได้รับมาโดยอัตโนมัติ)
   - **ไม่มีสิทธิ์** นำเข้า Excel, จัดการข้อมูลซ้ำ, org-data apply/rollback
   - ข้อมูลติดต่อรายบุคคลจำกัดตามสิทธิ์และความยินยอม (`consentGiven`)
   - ส่งออกได้เฉพาะข้อมูลสรุปตามขอบเขตที่อนุญาต
6. **ยังไม่สร้างบทบาทผู้จัดทำสถิติ** (เลื่อน) — ยังไม่มีผู้ใช้และข้อกำหนดที่ยืนยัน แถวใน ADR ก่อนหน้านี้ถูกถอดออก
7. **ข้อมูลส่วนบุคคลต้องผ่านการทบทวนโดยผู้รับผิดชอบด้านข้อมูลของคริสตจักรก่อนใช้งานจริง** ADR นี้ **ไม่ใช่การรับรองว่าสอดคล้อง PDPA หรือกฎหมายใด**

### เสนอ (Proposed — ยังไม่ยืนยันรายละเอียด)

ตารางสิทธิ์เริ่มต้น (R=read C=create U=update **A**=approve E=export; **delete ไม่มีในตาราง = เฉพาะ `admin`/`super_admin`**; `†` เฉพาะสมาชิกที่ `consentGiven = true`; `‡` ส่งออกเฉพาะข้อมูลสรุปและบันทึก audit log ทุกครั้ง):

| ผู้ใช้ (ขอบเขต) | ทะเบียนกลุ่ม | สมาชิก (ทั่วไป) | สมาชิก (อ่อนไหว) | รายงานรายสัปดาห์ | เป้าหมาย | สถิติ |
|---|---|---|---|---|---|---|
| ผู้นำ `care` ("พันธกิจ") ตามนิยาม `getLedGroupIds` (กลุ่มตน) | R U | R C U | — | R C U (ส่งเอง) | R | R (กลุ่มตน) |
| หัวหน้าแคร์ (ระดับกลางใหม่ + กลุ่มใต้) | R C* U | R U | R† | R **A** (รับรอง/ส่งกลับ) | R C U (แจกต่อ `care`) | R E‡ |
| หัวหน้าบอดี้ (บอดี้ + กลุ่มใต้) | R | R | R† | R (อ่านอย่างเดียว) | R C U (แจกต่อแคร์) | R E‡ |
| `team_lead` (ข้อเสนอ ยังไม่สร้าง) | R | R (ข้อมูลติดต่อตามสิทธิ์/ยินยอม) | R† | R (อ่านอย่างเดียว) | R C U (มอบบอดี้) | R E‡ |
| `admin` / `super_admin` (ของเดิม) | ตามเดิม | ตามเดิม | ตามเดิม | ตามเดิม | ตามเดิม | ตามเดิม |

`*` ใครสร้างกลุ่มใหม่ยังไม่ตัดสิน (S2) · แถว "หัวหน้าแคร์" ใช้ได้เมื่อระดับกลางมีอยู่จริง (ADR 002 — Proposed) · ตารางนี้ยกเว้นข้อ 5 เป็น **ข้อเสนอของผู้ร่าง ไม่ใช่ข้อสรุปของเจ้าของ**

- ผู้นำ `care` เห็นเบอร์โทรจริงเฉพาะสมาชิกกลุ่มตน ข้อมูลอ่อนไหว (วันรับเชื่อ สถานภาพครอบครัว บันทึกการติดตาม) เห็นได้ตั้งแต่หัวหน้าแคร์ขึ้นไปเฉพาะสมาชิกที่ยินยอม
- ก่อนลงมือต้องมี **security tests ใหม่** ซึ่งยังไม่มี: ขอบเขตครอบคลุมกลุ่มลูก, ผู้ใช้นอกขอบเขตถูกปฏิเสธทุกการกระทำ, ข้อมูลอ่อนไหวไม่รั่วข้ามขอบเขต, การส่งออกถูก audit, `team_lead` ถูกปฏิเสธทุกการกระทำที่ทำลายข้อมูล
- **ไม่แก้** `shared/roles.ts`, `groupAccess.ts` หรือโค้ด security ใดในรอบนี้

## Consequences

**ดี:** ไม่เพิ่มระบบสิทธิ์ที่สอง สิทธิ์เปลี่ยนตามผู้นำจริง และแยกสิทธิ์ทำลายข้อมูลออกจากสิทธิ์บริหารชัดเจน

**แย่:**
- ขอบเขตลำดับชั้นเพิ่ม query แบบ recursive และเสี่ยง "เห็นเกินสิทธิ์" ซึ่งไม่ปรากฏตอน build จึงต้องพึ่ง security tests
- **ต้องมีบัญชี Clerk สำหรับผู้นำ `care` ทุกคนที่ต้องส่งรายงาน** ซึ่งแผนเดิมจัดเป็น out-of-scope — ยังไม่ตัดสิน (S3) และผู้นำที่ไม่มีบัญชีส่งรายงานไม่ได้
- **ผู้นำเปลี่ยนตัวแล้วสิทธิ์อาจค้าง** ต้องมีกระบวนการถอนสิทธิ์ (S3)
- `team_lead` เป็นบทบาทใหม่ที่แตะไฟล์ของ Security (`USER_ROLES`, `shared/roles.ts`, ชุดสิทธิ์ฝั่ง client, การปิดบังข้อมูล, bootstrap) คอลัมน์ `users.role` ไม่ใช่ native enum (ARCHITECTURE R9) จึงไม่ต้อง migrate ตาราง แต่ต้องมีเทสต์ และ **ไม่มี UI มอบบทบาท** วันนี้
- **ความเสี่ยงอนุมัติตัวเอง:** ถ้าคนเดียวเป็นทั้งผู้นำ `care` และหัวหน้าแคร์ จะส่งและรับรองรายงานตัวเองได้ — ยังไม่มีกฎ (S7)

**เป็นกลาง:** `ministry_leader` ไม่ถูกเปลี่ยนความหมาย แต่ควรตรวจภายหลังว่า `PRIVILEGED_ROLES` ให้สิทธิ์เกินหน้าที่ฝ่ายงานหรือไม่ (นอกขอบเขต)

## Open decisions (ยังไม่ยืนยัน)

| # | เรื่อง |
|---|---|
| S2 | ใครสร้างกลุ่มใหม่ได้ (`C*`) |
| S3 | เชิญผู้นำเข้า Clerk หรือไม่ และกระบวนการถอนสิทธิ์ |
| S4 | การส่งออกระดับสมาชิก (รายคน) ให้ตำแหน่งใดได้บ้าง (ของ `team_lead` ตัดสินแล้วว่าเฉพาะสรุป) |
| S5 | การทบทวนข้อมูลส่วนบุคคลโดยผู้รับผิดชอบด้านข้อมูลของคริสตจักร (ต้องเกิดก่อนใช้งานจริง) |
| S6 | รูปถ่ายกิจกรรม/กลุ่ม: ใครเห็นได้ |
| S7 | กฎกันอนุมัติตัวเอง เมื่อผู้ส่งและผู้รับรองเป็นคนเดียวกัน |
| S8 | ช่องทางมอบบทบาท `team_lead` ก่อนมี UI จัดการบทบาท (วันนี้ทำได้ผ่าน DB/bootstrap เท่านั้น) |
| — | บทบาทผู้จัดทำสถิติ: **เลื่อน** จนกว่ามีผู้ใช้และข้อกำหนดจริง |

## Alternatives considered

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| เพิ่มบทบาท `body_leader` / `care_leader` ใน `USER_ROLES` | ซ้ำกับโครงสร้างใน `groups` สิทธิ์ค้างเมื่อเปลี่ยนผู้นำ และกลายเป็นระบบสิทธิ์ที่สอง |
| ให้หัวหน้าทีมเป็น `admin` | สิทธิ์ลบ นำเข้า และ org-data rollback เกินหน้าที่ |
| ให้หัวหน้าทีมเป็น `staff` | ไม่มีสิทธิ์ทำลาย แต่เห็นเบอร์จริงของสมาชิกทุกคนและส่งออกรายคนได้ |
| ใช้ `viewer` เป็นผู้จัดทำสถิติ | `viewer` เข้า `/api/reports` ไม่ได้ (และยังเลื่อนบทบาทนี้) |
| ให้ทุกคนเห็นข้อมูลสมาชิกทั้งหมดในสายของตน | เปิดเผยเกินจำเป็น ขัดเป้า G1 ใน `PRD.md` |
