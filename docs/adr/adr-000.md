# ADR 000: Clerk เป็น identity provider เดียวใน production

- **Status:** accepted
- **Date:** 2026-10-07 (บันทึกย้อนหลังจากการตัดสินใจที่มีอยู่แล้วในโค้ด)
- **Deciders:** เจ้าของโปรเจกต์
- **Supersedes:** —

## Context

แอปนี้เป็นระบบภายในของคริสตจักร ข้อมูลเป็นข้อมูลส่วนบุคคลของสมาชิก (ชื่อ, เบอร์โทร, ที่อยู่, บันทึกการเยี่ยมติดตาม)
ระบบต้องมี authentication ที่เชื่อถือได้ และ authorization ที่แยกบทบาทได้ (สมาชิกทั่วไป / อาสาสมัคร / ผู้ดูแล)

ตัวเลือกในทางทฤษฎีคือ เขียน auth เอง (session/JWT + ตาราง user + รีเซ็ตรหัสผ่าน) หรือใช้ผู้ให้บริการ identity
การเขียนเองหมายถึงต้องดูแล password hashing, การรีเซ็ตรหัสผ่าน, การยืนยันอีเมล, การป้องกันการโจมตี credential stuffing, และ surface การจัดการบัญชี — ทั้งหมดนี้ไม่มีส่วนใดที่ทำให้ระบบนี้ต่างจากแอปอื่น

## Decision

ใช้ **Clerk** เป็น identity provider **เดียว** ใน production ผ่าน `@clerk/express` ฝั่ง server และ `@clerk/react` ฝั่ง client
identity ถูก map ลงตาราง `users` ของเราเอง (ไม่ใช่ใช้ Clerk เป็นฐานข้อมูลผู้ใช้)
Authorization ทำที่ฝั่งเราผ่าน `shared/roles.ts` เท่านั้น

## Consequences

**ดี**
- ไม่ต้องดูแล password, การรีเซ็ต, การยืนยันอีเมล — ลดพื้นที่โจมตีที่ใหญ่ที่สุดของแอปประเภทนี้
- ได้ MFA และ session management ระดับ production โดยไม่เขียนเอง
- ฝั่ง client ได้ component พร้อมใช้ (`<SignIn/>`) ลดงาน UI ที่ต้องทดสอบเอง

**แย่**
- **ผูกกับผู้ให้บริการรายเดียว (vendor lock-in)** — การย้ายออกต้องสร้างระบบ auth ใหม่ทั้งชุด
- ผู้ใช้ต้องมี/สมัครบัญชี Clerk (แม้จะ sign-in ด้วยอีเมลก็ตาม) — เพิ่ม friction เทียบกับระบบบัญชีภายใน
- ต้องมี `CLERK_SECRET_KEY` และ publishable key ตลอดเวลา **ไม่มีแล้ว middleware จะ throw และทุก request จะได้ 500**
- ต้องมี webhook (`POST /api/webhooks/clerk`) เพื่อ sync ผู้ใช้ → เพิ่ม surface ที่ต้องป้องกันด้วย signature verification
- ค่าใช้จ่ายผูกกับจำนวนผู้ใช้ (MAU)

**เป็นกลาง**
- มีเส้นทาง auth ทางเลือกสำหรับ test (`PUNTAKIT_TEST_AUTH=1`) และ demo mode (`PUNTAKIT_DEMO_MODE=1`) ซึ่งต้องถูกกันไม่ให้ใช้ใน production

## Alternatives considered

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| Session/JWT เขียนเอง + ตาราง user ของเรา | ต้องดูแล password/รีเซ็ต/ยืนยันอีเมลเอง — งานมหาศาลและเสี่ยงกว่า โดยไม่ได้อะไรกลับมา |
| Auth0 / Supabase Auth / Firebase Auth | ทำงานเทียบเท่ากันได้ แต่ ณ เวลาตัดสินใจเลือก Clerk และไม่มีความจำเป็นที่พิสูจน์ได้ที่จะเปลี่ยน |
| OAuth ผ่าน Google เท่านั้น | คริสตจักรมีสมาชิกที่ไม่ใช่นักเทคโนโลยีและอาจไม่มีบัญชี Google — ต้องมีอีเมล/รหัสผ่านเป็นทางเลือกหลัก |
