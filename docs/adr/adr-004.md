# ADR 004: เวิร์กโฟลว์รายงานพันธกิจประจำสัปดาห์และนิยามตัวชี้วัด

- **Status:** proposed
- **Date:** 2026-10-09
- **Deciders:** เจ้าของโปรเจกต์ (session 2026-10-09 — **ยังไม่ผ่านการตรวจรับ ยังไม่ `accepted`**)
- **Supersedes:** — (ปรับ `MISSION_DOMAIN_PLAN` §9, §15, §16, §19 บางแถว ดู Context)

> ศัพท์ระดับองค์กร ดู [ADR 002](./adr-002.md) · สิทธิ์และบทบาท ดู [ADR 003](./adr-003.md) — ที่นี่ไม่ทำสำเนา

**สถานะการลงมือ: ยังไม่ได้สร้างตาราง ไม่ได้รัน migration ไม่ได้แก้ schema หรือโค้ด ไม่มี DDL และไม่มีเทสต์ของข้อกำหนดนี้ — การออกแบบดัชนีในเอกสารนี้ _ยังไม่ได้รับการพิสูจน์_ (ดู "ขอบเขตของการพิสูจน์")**

## Context

แผนเดิม (`MISSION_DOMAIN_PLAN` §9) กำหนด `weekly_reports` สถานะ `draft → submitted → acknowledged` หนึ่งรายงานต่อกลุ่มต่อสัปดาห์ จำนวนผู้เข้าร่วมคำนวณจากแถวรายชื่อ — **ตารางยังไม่ถูกสร้าง** และพึ่ง migration `0010_group_members_history` ที่ถูกกั้นด้วย pre-check กับฐานข้อมูลจริงซึ่งยังไม่ได้รัน

ช่องว่างและความไม่สอดคล้องในแผนเดิม:

1. ไม่มีฟิลด์ยืนยันว่า **กลุ่มจัดกิจกรรมจริงหรือไม่** ในสัปดาห์นั้น (ตัวชี้วัดหลักต้องใช้)
2. ไม่มีสถานะ "ส่งกลับให้แก้ไข" และแผนให้ `GROUP_MANAGE_ANY_ROLES` (ระดับ admin) รับรอง (แผน §16)
3. กฎ `UNIQUE (group_id, week_start)` (แผน §9/§15/§19) ขัดกับกฎ "แก้รายงานที่ส่งแล้ว → เก็บฉบับเก่าเป็น superseded" — **แก้แล้วด้วยทางเลือก ก** ด้านล่าง
4. ตัวอย่าง "สัปดาห์ 2–8 ต.ค. 2569" คือวันศุกร์–พฤหัสบดี (ตรวจกับปฏิทินแล้ว)
5. ไม่มีส่วนเป้าหมาย/สถิติในแผนเดิมและ `PRD.md`
6. แผน §19 มีแถวทดสอบ "weekly submit is limited to current members" ซึ่งขัดกับ Q26 (ผู้ส่ง = ผู้นำ)

## Decisions

### ตัดสินแล้ว (เจ้าของยืนยันใน session; ADR ยังไม่ `accepted`)

**ข้อมูลไหลทางเดียว:** ทะเบียน → รายงานรายสัปดาห์ → สถิติ → เป้าหมาย สถิติคำนวณจากข้อมูลต้นทางเสมอ ไม่ให้ระดับใดกรอกตัวเลขชุดเดียวกันซ้ำ

**สถานะรายงาน (Q5):** `draft → submitted → (needs_revision | acknowledged)` และ `superseded` สำหรับฉบับที่ถูกแทนที่ หัวหน้าแคร์ (ระดับกลาง — ดู ADR 002) รับรองหรือส่งกลับ หัวหน้าบอดี้และ `team_lead` อ่านอย่างเดียว ภาพรวมแสดง "ยังไม่ส่ง" รวม "ไม่มีแถว" กับ "มีแต่ `draft`" แต่รายละเอียดต้องแยกสองกรณีนี้

**Q26 — ผู้ส่งรายงาน:** ต้องเป็นผู้นำที่ได้รับอนุญาตตามนิยามเดียวกับ `getLedGroupIds` (`server/lib/groupAccess.ts`): **ผู้นำ** (`groups.leaderId`), **ผู้นำร่วม** (`groups.coLeaderId`) และ **ผู้ช่วยผู้นำ** (สมาชิกกลุ่มที่มีบทบาท `leader`/`assistant_leader`) **สมาชิกทั่วไปและเจ้าของบ้านที่เป็นเพียง `host` ไม่มีสิทธิ์ส่งโดยอัตโนมัติ** การสร้างบัญชีและเชิญผู้นำเข้าระบบเป็น Open Decision (ADR 003 S3)

**Q27 — ตัวชี้วัดรายงานวันจันทร์:**

| ตัวเลข | ความหมาย |
|---|---|
| **รับรองแล้ว X** | จำนวนกลุ่มที่รายงานว่าจัดกิจกรรมจริง **และ** รายงานได้รับการรับรองแล้ว — **เป็นตัวเลขทางการ** |
| **รอรับรอง Y** | จำนวนกลุ่มที่มีรายงานรอการตรวจรับ |
| **รวมตามที่รายงาน** | แสดงข้อมูลที่รายงานจริง โดยแยกสถานะการรับรอง — **ไม่ใช้แทนตัวเลขทางการ** |

ต้องแยกสี่กรณีนี้ออกจากกันเสมอ: (1) จัดกิจกรรมจริง (2) ส่งรายงานแล้วแต่ไม่ได้จัดกิจกรรม (3) รายงานที่รอรับรอง (4) ยังไม่ส่งรายงาน **ห้ามนับกลุ่มที่ไม่ได้ส่งรายงานว่าไม่ได้จัดกิจกรรม** (สอดคล้อง "NEVER TURN UNKNOWN DATA INTO FACT") **ตัวหารของอัตราการดำเนินงาน = กลุ่มที่มีสถานะ `active`** ผลที่ตามมา: อัตรา X ÷ ตัวหาร จะต่ำกว่าความจริงเมื่อมีรายงานรอรับรอง จึงต้องแสดง Y ติดกันเสมอ

**Q28 — รอบสัปดาห์:** จันทร์–อาทิตย์ ตามเวลาไทย เก็บ `weekStart` เป็นวันที่ล้วน ไม่ใช่ timestamp ปิดรอบก่อนการประชุมวันจันทร์ Dashboard เช็คชื่อเดิมเริ่มสัปดาห์วันอาทิตย์ (`server/routes/attendance.ts:689-691` ใช้ `getDay()` และเวลาท้องถิ่นของเซิร์ฟเวอร์) **ยังไม่ถูกแก้** บันทึกเป็น Technical Debt แยกต่างหาก (ไฟล์บันทึกนอก repo) **ห้ามเปลี่ยนวิธีนับของระบบเช็คชื่อในงานนี้**

**Q29 + W4 + Q31 — ประวัติรายงาน และข้อขัดแย้งที่แก้แล้ว (เจ้าของเลือกทางเลือก ก):**

กติกาที่ตกลง: แก้รายงานที่ส่งหรือรับรองแล้ว → สร้างฉบับใหม่สถานะ `draft`; ฉบับเดิมยังเป็นฉบับปัจจุบันและนับตามสถานะเดิมจนกว่าฉบับใหม่ถูกส่ง; เมื่อส่ง ฉบับเดิมถูกทำเครื่องหมาย `superseded` ข้อขัดแย้งที่พบ: ถ้าใช้ดัชนีเดียว `UNIQUE (group_id, week_start) WHERE superseded_at IS NULL` ระหว่างที่ร่างใหม่ยังไม่ถูกส่ง จะมีสองแถวที่ `superseded_at IS NULL` (ฉบับเดิมกับร่าง) และฐานข้อมูลจะปฏิเสธ จึงแยกเป็น **สองดัชนี**:

| ดัชนี | นิยาม (ออกแบบ — ยังไม่ใช่ DDL) | จำกัดอะไร |
|---|---|---|
| **A — ฉบับปัจจุบันที่ไม่ใช่ draft** | `UNIQUE (group_id, week_start) WHERE superseded_at IS NULL AND status <> 'draft'` | ต่อกลุ่มต่อสัปดาห์ มีฉบับปัจจุบันที่ส่งแล้วได้ **ไม่เกินหนึ่งฉบับ** (สถานะ `submitted`, `needs_revision` หรือ `acknowledged`) |
| **B — ร่างที่ยังเปิดอยู่** | `UNIQUE (group_id, week_start) WHERE status = 'draft'` | ต่อกลุ่มต่อสัปดาห์ มีร่างเปิดอยู่ได้ **ไม่เกินหนึ่งฉบับ** |

**ฟิลด์ที่เกี่ยวข้อง (เสนอ ไม่ใช่ DDL):** `version`, `supersedes_id` (ชี้ฉบับที่ร่างนี้จะมาแทน), `superseded_at`

**Q31 — `needs_revision`:** เมื่อรายงานถูกส่งกลับให้แก้ **สร้างฉบับใหม่** เหมือนกรณีส่ง/รับรองแล้ว ไม่แก้ในแถวเดิม ฉบับที่ถูกส่งกลับ (`needs_revision`) ยังเป็นฉบับปัจจุบันที่ไม่ใช่ draft จนกว่าฉบับใหม่จะถูกส่ง

**ลำดับการส่งฉบับใหม่ (ต้องเป็นชุดการเขียนเดียวที่ทำพร้อมกันทั้งหมดหรือไม่ทำเลย — atomic):**

1. ทำฉบับเดิม (ฉบับปัจจุบัน) เป็น `superseded` (ตั้ง `superseded_at`)
2. **แล้วจึง** เปลี่ยนฉบับใหม่จาก `draft` เป็น `submitted` (ตั้ง `submitted_at`, ผู้ส่ง)

ลำดับนี้สำคัญเพราะดัชนี A ถูกตรวจทีละคำสั่ง (อนุมานจากพฤติกรรมของ unique index ใน Postgres ยังไม่ได้ทดสอบกับตารางนี้): ถ้าเลื่อนฉบับใหม่ก่อน จะมีสองแถวที่ผ่านเงื่อนไขของดัชนี A ชั่วขณะ ในโค้ดปัจจุบัน ตัวช่วย `runAtomically` (`server/lib/atomicWrites.ts`) รันชุดคำสั่งเป็นหน่วยเดียว (neon-http ใช้ `db.batch` ซึ่งสร้างคำสั่งล่วงหน้าและอ่านผลระหว่างทางไม่ได้; ไดรเวอร์อื่นใช้ transaction) การอ่านรหัสฉบับปัจจุบันต้องทำก่อนสร้างชุดคำสั่ง ถ้าระหว่างนั้นมีผู้อื่นเปลี่ยนฉบับปัจจุบัน ชุดคำสั่งควรล้มทั้งชุดเพราะดัชนี A (ออกแบบให้ล้มอย่างปลอดภัย — **ยังไม่พิสูจน์**)

**ผลต่อการนับและประวัติ:**
- **ประวัติฉบับเก่าถูกเก็บเสมอ** ไม่ลบ แต่ละฉบับเก็บผู้ส่ง ผู้ตรวจ และเวลา เชื่อมกันด้วย `supersedes_id`
- **ระหว่างที่ฉบับแก้ไขเป็น `draft` ฉบับปัจจุบันเดิมยังนับตามสถานะเดิม** — ฉบับเดิมที่ `acknowledged` และจัดกิจกรรมยังเป็นส่วนของ **X (ตัวเลขทางการ)** ต่อไป ส่วนร่างไม่ถูกนับในหมวดใดเลย (ไม่ใช่แม้แต่ Y)
- **เมื่อฉบับใหม่ถูกส่ง** ฉบับเดิมเป็น `superseded` และฉบับใหม่เป็น `submitted` (ยังไม่รับรอง) กลุ่มนั้นจึง **ย้ายจาก X ไปเป็น Y (รอรับรอง)** จนกว่าหัวหน้าแคร์จะรับรองฉบับใหม่ นี่คือผลที่ตามมาของกติกา ไม่ใช่การตัดสินใจใหม่ — แสดง Y ติดกับ X เสมอ (Q27) เพื่อไม่ให้ดูเหมือนผลงานหาย
- กลุ่มที่มีแต่ร่างแรกที่ยังไม่เคยส่ง จัดอยู่หมวด 4 ("ยังไม่ส่งรายงาน") เหมือนเดิม

### ขอบเขตของการพิสูจน์ (สำคัญ)

การออกแบบสองดัชนีนี้ **ยังไม่ได้รับการพิสูจน์จากการอ่านเอกสารหรือโค้ด** สิ่งที่มีหลักฐานจริง:
- repo มี test ที่แสดงว่า partial unique index **ตัวเดียว** ทำงานบน PGlite ("ยังกันสองแถวปัจจุบันได้" — `server/db/pendingMigration0010.test.ts` กับ SQL ที่ `server/db/pending/0010_group_members_history.sql`)

สิ่งที่ **ยังไม่มีหลักฐาน** (`NOT VERIFIED`): ดัชนี A+B ทำงานร่วมกันอย่างที่ตั้งใจ · ลำดับ supersede→submit ผ่านในชุดเดียวบน neon-http และ PGlite · ล้มทั้งชุดเมื่อมีการแข่งกัน · `shared/schema.ts` ยังไม่มี partial index สักตัว และไม่ได้ตรวจว่า drizzle-kit 0.31 สร้าง predicate แบบนี้ได้ถูกต้องในรีโปนี้ — ต้องมีเทสต์บน PGlite ก่อนถือว่าออกแบบเสร็จ

### เสนอ (Proposed — ผู้ร่างเสนอ ยังไม่ยืนยัน)

- **ผู้ถูกรายงาน:** หน่วยล่างสุด (`care`) เท่านั้น และตัวหาร "active" = แถว `care` ที่ `status='active'` และไม่ถูกลบ (ผูกกับ ADR 002 Q23/O3 — ถ้าเปลี่ยน ต้องทบทวน)
- **การจัดหมวดไม่ซ้ำ** ต่อกลุ่มต่อสัปดาห์ จัดจาก **ฉบับปัจจุบันที่ไม่ใช่ draft** (นิยามตามดัชนี A):

| หมวด | เงื่อนไข |
|---|---|
| 1 จัดกิจกรรมจริง (= X, ทางการ) | `acknowledged` และ `held = true` |
| 2 ส่งแล้ว แต่ไม่ได้จัด | `acknowledged` และ `held = false` |
| 3 รอรับรอง (= Y) | `submitted` ที่ยังไม่รับรอง (ไม่ว่า `held`) |
| 4 ยังไม่ส่งรายงาน | ไม่มีฉบับปัจจุบันที่ไม่ใช่ draft (ไม่มีแถว หรือมีแต่ `draft`) |
| ยังไม่จัดหมวด | `needs_revision` — ดู W8 |

- ฟิลด์ที่ต้องเพิ่มในอนาคต (**เสนอ ไม่ใช่ DDL**): `held`, `notHeldReason`, ผู้ตรวจ/เวลาตรวจ/หมายเหตุการส่งกลับ, `superseded_at`, `version`, `supersedes_id`

## Consequences

**ดี:** ตัวเลขรายงานวันจันทร์มาจากข้อมูลจริงทางเดียว แยก "ไม่รู้" ออกจาก "ไม่ได้ทำ" ตัวเลขทางการไม่ปนข้อมูลที่ยังไม่ตรวจ รอบสัปดาห์ตรงกับการประชุม และตัวเลขของฉบับเดิมไม่หายระหว่างกำลังแก้

**แย่:**
- ดัชนี A ต้องจำเงื่อนไขสองส่วน (`superseded_at IS NULL` และ `status <> 'draft'`) ทุกครั้งที่ query "ฉบับปัจจุบัน" ถ้าลืมจะนับร่างปนฉบับปัจจุบัน
- กฎ "ร่างเปิดได้ 1 ฉบับ" (ดัชนี B) เป็นกติกาที่ตกลงเมื่อเลือกทางเลือก ก แต่ยังมีรายละเอียดที่ไม่ได้ตัดสิน (W10, W11)
- ลำดับ supersede→submit ต้องถูกต้องเสมอ ผู้พัฒนาที่สลับลำดับจะทำให้การส่งล้ม (ล้มอย่างปลอดภัย แต่เป็นบั๊กใช้งานจริง) ต้องมีเทสต์
- ดัชนีทั้งสองจะเป็น partial index ตัวแรกในไฟล์ `shared/schema.ts` (ยังไม่เคยมี) การสร้างต้องผ่านขั้นตอน migration ปกติของรีโป ซึ่งยังไม่ได้ทดสอบกับ predicate แบบนี้
- การส่งฉบับแก้ไขทำให้กลุ่มที่เคยเป็น X ตกเป็น Y ชั่วคราว ผู้อ่านรายงานอาจเข้าใจว่าผลงานลดลง
- ตัวเลขทางการนับเฉพาะที่รับรองแล้ว ถ้าหัวหน้าแคร์ยังไม่รับรองก่อนประชุม X จะต่ำกว่าความจริง (จึงต้องแสดง Y)
- ตัวหาร "active" พึ่งวินัยการดูแลทะเบียน ถ้ากลุ่มหยุดแต่ยังเป็น `active` อัตราจะต่ำเกินจริง
- ผู้นำที่ไม่มีบัญชีส่งรายงานไม่ได้ (ADR 003 S3) กลุ่มนั้นจะอยู่ในหมวด 4
- ผู้รับรองคือหัวหน้าแคร์ซึ่งเป็นระดับกลางที่ยังไม่มีในโค้ดและข้อมูล (ADR 002) — ถ้า Q24 ไม่สนับสนุน Q23 ต้องทบทวน
- การเก็บ `weekStart` เป็นวันที่ล้วนต่างจาก dashboard เช็คชื่อที่เริ่มวันอาทิตย์ ตัวเลข "สัปดาห์นี้" สองที่จึงไม่ตรงกัน
- ความเสี่ยงอนุมัติตัวเอง (ADR 003 S7)

**เป็นกลาง:** แผน §9 ยังเป็นที่มาของขั้นตอนกรอก (STEP 1–4) ADR นี้ไม่เปลี่ยนขั้นตอนนั้น

## Open decisions (ยังไม่ยืนยัน)

## Alternatives considered

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| ให้แต่ละระดับกรอกตัวเลขสรุปเอง | ตัวเลขไม่ตรงกัน เป็นปัญหา Excel ที่กำลังแก้ |
| นับ "ไม่ส่งรายงาน" เป็น "ไม่ได้จัด" | อนุมานค่าที่ไม่มีหลักฐาน |
| นับ `submitted` ที่ยังไม่รับรองเป็นตัวเลขทางการ | ปนข้อมูลที่ยังไม่ตรวจกับผลที่รับรองแล้ว (ค่าเริ่มต้นเดิมของร่างแรก ถูกแทนที่ตาม Q27) |
| สัปดาห์เริ่มวันอาทิตย์ตาม dashboard เช็คชื่อ | ไม่ตรงรอบประชุมวันจันทร์ และผูกกับเวลาท้องถิ่นของเซิร์ฟเวอร์ |
| ต้องรับรองหลายชั้น | ช้า และข้อกำหนดคือหัวหน้าแคร์รับรองคนเดียว |
| W4 ทางเลือก **ข** — ตัวบ่งชี้ `is_current` ที่สลับตอนส่ง | เจ้าของไม่ได้เลือก (session 2026-10-09) |
| W4 ทางเลือก **ค** — เก็บฉบับร่างในตารางแยก | เจ้าของไม่ได้เลือก (session 2026-10-09) |
| ดัชนีเดียว `UNIQUE … WHERE superseded_at IS NULL` ตามข้อความแรกของ Q29 | ชนกันเองเมื่อมีร่างข้างฉบับปัจจุบัน (ดูข้อขัดแย้งด้านบน) |
| `needs_revision` แก้ในแถวเดิม (Q31 ข้อ 1) | เจ้าของเลือกข้อ 2 (สร้างฉบับใหม่) |
